# Davis Paper Protocol Investigation and Plan

**Scope:** Read-only comparison of the local Davis implementation with the MGraphDTA paper and public author reference code. No training was run and no existing code, data, checkpoints, summaries, or results were changed. The existing aggregate in `results/davis/multiseed_validated_20261017/` remains untouched.

## Executive summary

The repository implements the central MGraphDTA architecture and uses the correct Davis pKd conversion and a fixed 5,010-interaction test fold. Its current training code keeps that test fold out of validation and checkpoint selection. However, the present multi-seed results (seeds 44–46) use a capped 150-epoch, 50-step schedule, batch size 32, and a random 10% validation split; the paper reports batch size 512 and five-fold Optuna tuning on Davis training data. The paper says Davis regression experiments were repeated three times with different random seeds. These differences mean the current three-seed aggregate is a useful separate experiment, not evidence of a complete paper reproduction.

The model architecture mostly matches the authors’ code and ESI-selected structure. A concrete preprocessing discrepancy remains: the author preprocessing applies per-molecule min–max scaling to the atom-feature matrix; local `src/preprocessing.py` returns raw feature values. The graph edge attributes present in the author preprocessing are not passed into its GraphConv model, and are likewise unused by the local model.

## Confirmed requirements versus unresolved details

### Confirmed by the paper or ESI evidence

1. Davis is the 68-drug, 442-target, 30,056-interaction regression benchmark; pKd is the target and 10 μM sentinel values map to pKd 5 (§2.7, Table 1).
2. Davis hyperparameter tuning is described as Optuna five-fold CV performed on the Davis training set (§2.8); chosen hyperparameters are then fixed for other datasets.
3. Adam, LR `0.0005`, and batch 512 are the paper’s reported training setup (§2.8).
4. The MGNN uses three multiscale blocks, eight graph-convolution layers per block, and three transition layers; the paper calls this 27 conceptual layers (§2.8).
5. ESI S3 selected three multiscale blocks, eight layers/block, hidden width 64, and three MCNN branches.
6. Davis regression evaluation includes MSE, CI, and `r_m²`; regression results are repeated across three random seeds (§3.2).

### Reference-code behavior, not safe to equate with paper protocol

The public regression training script sets 3,000 logical epochs, 50 steps per reported epoch, patience 400, Adam `5e-4`, and batch 512. Critically, it evaluates the fixed test loader every 50 steps and saves/stops based on test loss. That creates test-set model-selection leakage. The exact public `dev` revision was not pinned in this audit. Do not adopt this test-based selection behavior for a scientifically independent evaluation.

### Unresolved / assumptions

- The full ESI PDF, especially S1/S2 feature definitions and all of S3, is not in the local repository. Obtain and archive it before declaring exact feature and hyperparameter search parity.
- The main article does not specify epoch count, patience, validation checkpoint rule, Optuna trial count/sampler/seed, fold assignment details, or how to select the final epoch after cross-validation. The reference script does not resolve these safely because it selects on test loss.
- Local Davis input files appear structurally consistent with the standard Davis files and have matching train/test interaction counts, but no hashes or upstream source/version record proves bytewise identity.
- Pin an author repository commit and compatible package environment. The online source inspected here was the mutable `dev` branch; its README lists old PyTorch, PyG, and RDKit dependencies.
- Confirm that local atom feature values (including RDKit valence fields) match the author code on a fixed molecule set after applying the author’s normalization.
- Clarify the precise standard random train/test split used for Table 3 and its relationship to the standard fold files before comparing the local aggregate or baseline values to Table 3.

## One concrete next experiment

Run a **protocol-auditable Davis tuning-and-evaluation experiment** as a new, separately named result set. This is a recommended protocol that follows the paper’s stated intent while avoiding the test leakage in the public training script. It is not a claim that every unspecified paper detail has been recovered.

### Gate before any training

Obtain the ESI PDF and a pinned author-code revision; record the revision/hash and dependency versions. Verify raw Davis files against the cited source using file hashes. Compare local and author atom features for several fixed molecules. Resolve the per-molecule feature scaling discrepancy before fitting. Freeze the split manifest and write down any protocol choice that the paper does not specify.

### Split and tuning

- Preserve the existing published Davis test fold (5,010 interactions) and never load it during tuning, validation, early stopping, or checkpoint selection.
- Use the five provided training-fold lists as five cross-validation folds: for each fold, fit on the other four lists and validate on the held-out list. Record the exact interaction indices for every fit/validation partition.
- Run Optuna using only those five training folds. Search the ESI S3 ranges and report selected values; fix the confirmed selected architecture at 3 blocks, 8 layers/block, 64 intermediate channels, and 3 MCNN branches when the tuning results reproduce those values. Use Adam, LR `0.0005`, batch 512, and MSE. Do not tune on the test fold.
- Because the paper does not give an epoch/checkpoint rule and the reference code uses test loss, pre-register a defensible rule: select the epoch by validation MSE within each fold, and record the fold-best epochs. For the final fits, use the median best epoch across folds as a fixed training duration; train on all 25,046 training interactions for that duration. This epoch aggregation is an explicit project protocol choice, not a reported paper fact.

### Final evaluation and repetition

- Freeze the hyperparameters and epoch duration before final fitting. Train three independent final models with three declared seeds to match the paper’s reported repetition count; use identical train/test indices and the same frozen settings for each seed.
- Select each final model at the pre-registered fixed epoch, not by test metrics. Evaluate each checkpoint on the 5,010-row test fold once after all choices are frozen.
- Report per-seed MSE, CI, and `r_m²` as paper-comparison metrics; include RMSE as a supplementary metric. Report mean and sample standard deviation across the three seeds. Keep these separate from the existing baseline and validated capped-run aggregate.

### Required new artifacts

Store everything under a new root, e.g. `results/davis/paper_protocol_<date>/`, and refuse to reuse a non-empty root. Include:

- `protocol_manifest.json`: raw/processed data SHA-256 hashes, exact fold-index hashes, software/hardware versions, author source commit, seed list, fixed settings, and protocol choices marked as assumptions.
- `optuna_study.db` and exported trial table/JSON: search space, sampler, seed, objective, fold scores, and selected configuration.
- Per-fold split manifests, training histories, best-validation checkpoints, and epoch-selection metadata.
- Frozen final configuration and three per-seed final checkpoints, histories, and checkpoint metadata.
- Per-seed test predictions with row identifiers, individual metrics JSON, and a summary with mean and sample SD.
- A report recording that test indices were not accessed until final evaluation, plus any deviations, run failures, and CUDA nondeterminism limitations.

## Hidden-channel mapping evidence update (2026-10-23; supersedes the mapping blocker above)

The paper's conceptual hidden width is now mapped to local `growth_rate` based on architecture semantics, not on matching numeric candidate values. The publisher's article §§2.2–2.3 defines a graph-convolution operation \(H\) that maps an input of width \(d\) to output width \(h\) (Eq. 1); Eq. 3 applies \(H\) to the concatenation of the initial features and earlier dense outputs. Thus each conceptual dense graph-convolution step contributes an \(h\)-wide output to the multiscale concatenation. Table S3's row, “The hidden channel number of each graph-convolutional layer,” is supported as the \(h\) output width at that conceptual layer boundary. The article's Fig. 4 depicts the same dense concatenation. See the [official RSC article](https://pubs.rsc.org/en-us/content/articlehtml/2022/sc/d1sc05180f) and the [official RSC ESI, Table S3](https://www.rsc.org/suppdata/d1/sc/d1sc05180f/d1sc05180f1.pdf).

This supports the local correspondence `Table S3 h` → `MGNN.hidden_channels` → `DenseLayer growth_rate`, where each DenseLayer appends exactly `growth_rate` channels. The pinned author release at `references/mgraphdta_official/author_repo/regression/model.py` realizes that conceptual unit with two physical `GraphConv` modules: `conv1` emits `growth_rate * bn_size` (with the regression model's `bn_size=2`) and `conv2` emits `growth_rate`, which is the appended dense output. The released stem has 32 channels; transition layers halve their accumulated input width. Those are implementation details of the released bottleneck realization, not reasons to reinterpret S3 as requiring every physical `GraphConv` to emit h. At selected h=64, local physical DenseLayer outputs are 128 then 64; stem and transition outputs are likewise not all 64. The final MGNN projection width 96 is explicit in the author release (`filter_num=32`, output `filter_num*3`) and local implementation; the article's Eq. 2 states a graph readout but does not give that numeric width in the cited main-text equation.

One equation detail remains ambiguous: Eq. 4 describes transition compression as half the input width, but its printed dimension \(d + (N−1)h\) appears inconsistent with Eq. 3's initial feature plus N dense outputs and with the released code's `input_width + N*growth_rate` calculation. The local code follows the released implementation and halves the resulting concatenated width. This indexing/dimension discrepancy does not change the supported meaning of h as the output width appended per conceptual dense step, but it prevents claiming exact equation-to-tensor identity for that transition expression.

Existing focused tests already exercise this mapping across all S3 choices: `tests/test_mgnn.py::test_s3_hidden_channel_choices_preserve_depth_shapes_and_finite_readout` asserts bottleneck `2h`, appended output `h`, dense concatenation and halved transitions; `tests/test_mgraphdta.py::test_s3_hidden_channel_choices_produce_finite_scalar_affinity_predictions` checks integrated predictions; `tests/test_mgnn.py::test_default_hidden_width_preserves_legacy_state_dict_shapes` preserves default checkpoint shapes.

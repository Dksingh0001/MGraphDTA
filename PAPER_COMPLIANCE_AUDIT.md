# MGraphDTA Paper Compliance Audit

**Scope:** read-only comparison of the repository implementation, saved artifacts and the original paper. No training was launched and no existing project file was changed for this audit.

**Primary reference:** Yang et al., “MGraphDTA: deep multiscale graph neural network for explainable drug–target binding affinity prediction,” *Chemical Science* 13 (2022), 816–833, DOI [10.1039/D1SC05180F](https://pubs.rsc.org/en-us/content/articlehtml/2022/sc/d1sc05180f). References below use its section and table numbers. Exact atom-feature definitions and tuning ranges are in ESI Tables S1–S3. The project contains `bio_paper.pdf`; local text extraction was unavailable in this environment, so the paper’s published RSC text and its linked ESI were used to check those details.

## Overall assessment

The repository implements the core two-tower MGraphDTA design: molecular graphs, a deep dense MGNN, three-scale protein CNN, affinity-regression head, and validation-selected checkpoint. The implementation has meaningful structural correspondence to the paper, but the current multi-seed runs are a **capped, materially different training protocol**, the Davis split/preprocessing provenance needs confirmation against the paper’s exact evaluation setup, and the multi-seed summary is internally inconsistent with saved artifacts. Therefore, the evidence does **not** support calling this a complete reproduction of the paper.

## Findings by area

### 1. Molecular graph construction and atom/bond features

**Paper:** Section 2.1 describes RDKit conversion of SMILES into molecular graphs with vertex features and adjacency. Exact vertex feature details are delegated to ESI Tables S1–S2. The paper’s graph convolution aggregates neighboring atom features; it does not describe a separate learned bond-feature encoder in the main methods.

**Code:** `src/preprocessing.py`, `smiles_to_mol`, `extract_atom_features_22dim`, and `extract_graph_structure` parse SMILES using RDKit, generate 22 node features, and create bidirectional `edge_index` connectivity for bonds. The code has no edge attributes. Features include atom-symbol one-hot, atomic number, donor/acceptor flags, aromaticity, hybridization, hydrogen counts, valences, charge, and radical electrons. `src/dataset.py:DavisDataset.__getitem__` rebuilds these features for each fetched interaction.

**Status: PARTIAL MATCH.** RDKit molecular graphs and adjacency-style topology match the paper’s main description. Exact feature parity cannot be established from code comments/tests alone; the 22-feature vector must be compared element-by-element with ESI S1–S2. No bond attributes are present; confirm this agrees with the authors’ reference implementation/ESI rather than assuming bond features are required.

**Evidence:** `src/preprocessing.py`; `src/dataset.py`, `DavisDataset.__getitem__`; paper §2.1 and ESI S1–S2.

**Next:** Compare the implemented feature ordering, values, unknown-element behavior, and RDKit settings against ESI S1–S2 and the authors’ released preprocessing code; document any intentional differences.

### 2. MGNN, dense blocks, transitions, and layer counting

**Paper:** Sections 2.2–2.3 and the architecture discussion specify neighbor aggregation, node-level batch normalization followed by ReLU, dense connections, three multiscale blocks with `N=8`, three transition layers, and global average readout. Section 2.8 reports 27 graph convolutional layers.

**Code:** `src/models/mgnn.py` uses PyG `GraphConv`, `NodeLevelBatchNorm`, and ReLU. There are three `MultiscaleBlock`s of eight `DenseLayer` units, each with dense concatenation; three transitions halve channels; `global_mean_pool` and a linear layer produce a 96-dimensional drug embedding. The source explicitly counts 27 paper-level stages (24 DenseLayer units + 3 transitions, excluding `conv0`) but has 52 literal `GraphConv` modules because each dense unit has two bottleneck graph convolutions, in addition to `conv0`.

**Status: PARTIAL MATCH.** The named block layout, normalization, transition, and readout correspond closely. The layer-count convention is not literal: calling the model “27 graph convolutional layers” hides that the implementation executes 52 `GraphConv` modules. The paper’s wording alone does not resolve this convention; reconcile against its architecture figure/equations and authors’ code before claiming exact depth parity.

**Evidence:** `src/models/mgnn.py`, `GraphConvBn`, `DenseLayer`, `MultiscaleBlock`, `MGNN.__init__`, `MGNN.forward`; paper §§2.2–2.3, 2.8.

**Next:** Make a layer-by-layer mapping from paper Figure 4/equations and official implementation, and state both logical block depth and physical convolution count in any reproduction report.

### 3. Protein sequence encoding and MCNN

**Paper:** Section 2.1 uses an integer amino-acid vocabulary, maximum protein length 1200, and trainable embedding dimension 128. Section 2.4 uses three branches with stacked 3×3 convolutions giving receptive fields 3, 5, and 7; each convolution is followed by ReLU, branch features are max-pooled, concatenated, and linearly projected.

**Code:** `src/preprocessing.py:preprocess_protein` maps the sequence to tokens, pads/truncates to 1200, and reserves token 0 for padding. `src/models/mcnn.py:MCNN` embeds to 128 dimensions; `StackCNN` creates 1/2/3 valid-width 3-wide convolutions with ReLU and adaptive max pooling, concatenates 96-channel outputs, and projects to 96 dimensions.

**Status: MATCH.** The stated sequence length, embedding dimension, branch receptive fields, activation, max pooling, concatenation, and projection match the paper’s description. Vocabulary edge cases (unknown letters, padding, and truncation) still deserve data validation but do not change the described core architecture.

**Evidence:** `src/preprocessing.py:VOCAB_PROTEIN`, `MAX_PROTEIN_LEN`, `preprocess_protein`; `src/models/mcnn.py:StackCNN`, `MCNN`; paper §§2.1, 2.4.

**Next:** Confirm the vocabulary ordering and padding/truncation behavior match the authors’ released preprocessing exactly, especially for ambiguous amino-acid symbols.

### 4. MLP and affinity-regression output

**Paper:** Section 2.5 concatenates the drug and protein representations and passes them to an MLP for a scalar affinity prediction. The paper specifies MSE loss and dropout 0.1 in its MLP description.

**Code:** `src/models/mgraphdta.py:MGraphDTA` concatenates the two 96-dimensional vectors. The head is Linear(192→1024) → ReLU → Dropout(0.1) → Linear(1024→1024) → ReLU → Dropout(0.1) → Linear(1024→256) → ReLU → Dropout(0.1) → Linear(256→1). `src/train.py:fit` uses `nn.MSELoss` by default.

**Status: PARTIAL MATCH.** Scalar regression, concatenated encoders, MSE, and dropout match. The paper’s “three linear transformation layers” wording is ambiguous about whether that count includes the final scalar-output layer; this implementation contains four Linear modules. Its exact hidden widths should be checked against ESI Table S3, which the main text directs readers to for detailed hyperparameters.

**Evidence:** `src/models/mgraphdta.py:MGraphDTA`; `src/train.py:fit`; paper §2.5 and ESI S3.

**Next:** Check the classifier widths/depth against ESI S3 and the authors’ code; do not alter the model based only on an ambiguous prose layer count.

### 5. Davis data, preprocessing, labels, and splits

**Paper:** Section 2.7 and Table 1 describe Davis with 68 compounds, 442 proteins, and 30,056 drug–target pairs. Kd values are transformed to pKd; non-binding values are recorded at 10 μM (pKd 5). The article also reports a filtered Davis variant and describes its independent-test plus five-fold protocol separately. Section 3.3 cautions about random splits and evaluates more demanding drug/target separation settings.

**Code:** `src/dataset.py:load_raw_davis_data` reads the Davis ligand/protein dictionaries, `Y`, and predefined `train_fold_setting1.txt`/`test_fold_setting1.txt`. `prepare_davis_tables` expands the interaction matrix and computes `9 - log10(Kd in nM)`, then flattens the provided training folds into one training table and uses the provided test indices as test. `src/train.py:train_davis` splits only the loaded training table into train/validation subsets with `split_train_validation`; it builds/evaluates the test dataset only after loading the best validation checkpoint.

**Status: PARTIAL MATCH.** The data source format, pKd transformation, and 10 μM Davis labels are consistent with the benchmark description, and the fixed test indices are not used for checkpoint selection in the training path. However, the code’s validation split is a seeded random 10% interaction-level split, while the paper describes five-fold CV for tuning and multiple evaluation/split protocols. The repository does not establish that its exact predefined test indices and test metrics are the same protocol used for Table 3. It also lacks a full audit trail validating row counts, index provenance, or filtered Davis preparation.

**Evidence:** `src/dataset.py:load_raw_davis_data`, `prepare_davis_tables`, `DavisDataset`; `src/train.py:split_train_validation`, `train_davis`; paper §§2.7, 3.3 and Table 1.

**Next:** Verify checksums/counts and exact train/test indices against the paper’s cited Davis data and original MGraphDTA evaluation code. Reproduce the paper’s tuning/evaluation split before making metric-to-metric claims.

### 6. Optimizer, learning rate, batch size, epochs, stopping, checkpoint

**Paper:** Section 2.8 reports Adam, learning rate 0.0005, batch size 512, and Davis hyperparameter optimization on the training data under five-fold cross-validation with Optuna; the selected settings were then fixed for other datasets. Detailed hyperparameters are in ESI Table S3. The main paper does not establish the current project’s 150-epoch/50-step schedule as the paper’s protocol.

**Code:** `src/train.py:fit` uses Adam and MSE. Default values are LR `5e-4`, batch size 512, 1000 epochs, 50 steps/epoch, patience 400. `scripts/run_multiseed.ps1` overrides this with 150 epochs, 50 steps/epoch, batch size 32, LR `0.0005`, patience 30, validation fraction 0.1, CUDA, and `--no-deterministic`. It saves a checkpoint whenever validation MSE improves and stops if patience is exhausted. Current seed metrics show 150 completed epochs and `stopped_early=false` for seeds 44, 45, and 46; each selected checkpoint was at its best validation epoch.

**Status: DIFFERENT for current multi-seed protocol; PARTIAL MATCH for defaults.** Adam and LR match. The multi-seed runs use a substantially smaller batch, capped epoch count, and truncated 50-step epochs, so their training exposure is not a full reproduction of the paper’s reported setup. The default 1000/50 and patience values also do not document the paper’s Optuna tuning procedure. Checkpoint selection by validation loss is methodologically appropriate, but exact selection parity with the paper is not demonstrated.

**Evidence:** `src/train.py:DEFAULT_*`, `fit`, `train_davis`; `scripts/run_multiseed.ps1`; seed-specific `final_metrics.json`; paper §2.8 and ESI S3.

**Next:** Recover the exact selected hyperparameters and training schedule from ESI S3/reference code and carry out the five-fold tuning/evaluation protocol on training-only data before labeling results a reproduction.

### 7. Evaluation metrics

**Paper:** Section 3.2 / Tables 3–4 report MSE, CI, and modified squared correlation `r_m²` for Davis/KIBA/Metz regression. The paper’s reported Davis Table 3 values for MGraphDTA are MSE 0.217, CI 0.879, and `r_m²` 0.673. RMSE is used for the filtered Davis comparison (Table 5), not as one of the three metrics in that main Davis table.

**Code:** `src/metrics.py` implements MSE, `sqrt(MSE)` RMSE, pairwise concordance index with half-credit ties, and the modified squared-correlation formula. `src/train.py:evaluate_test_metrics` emits all four; final metrics are computed only after restoring the best validation checkpoint.

**Status: PARTIAL MATCH.** MSE, CI, and `r_m²` are present and the stored baseline’s CI/`r_m²` are close to the published rounded values. The baseline MSE is 0.257041 (vs paper Table 3 0.217), so results do not match numerically. RMSE is a useful derived report but is not one of the paper’s headline Table 3 metrics. Because split, preprocessing parity, validation procedure, and training exposure differ or remain unverified, the metric difference is not a controlled reproduction comparison.

**Evidence:** `src/metrics.py`; `src/train.py:evaluate_test_metrics`, `train_davis`; `results/davis/run_112_backup/evaluation_metrics_corrected.json`; paper Table 3 and §3.2.

**Next:** Once data/split and training protocol are verified, evaluate the paper-matched test set with the same metric definitions and report unrounded values plus protocol details.

### 8. Grad-AAM and interpretability

**Paper:** Section 2.6 defines Grad-AAM using affinity gradients at the final MGNN graph-convolution activations to weight channels and create atom-level importance. Section 3.5 evaluates explanations against chemical/pharmacological interpretation, including structural alerts in ToxCast examples; the paper’s abstract describes this as evidence of useful explanations.

**Code:** `src/explainability/grad_aam.py:GradAAM.attribute` hooks `drug_encoder.transition3`, differentiates the scalar prediction with respect to activations, averages gradients by channel, normalizes channel weights and atom scores, and restores model mode/hook state. `tests/test_grad_aam.py` checks the formula on a toy model. Example generation exists in `scripts/generate_grad_aam_examples.py`.

**Status: PARTIAL MATCH.** The implementation follows the core gradient-to-final-layer atom attribution idea and has unit-level behavioral coverage. That is evidence of implementation, not scientific validation. The repository does not show a replicated ToxCast study, blinded expert assessment, comparison to the paper’s examples, or stability/faithfulness evaluation.

**Evidence:** `src/explainability/grad_aam.py`; `tests/test_grad_aam.py`; `scripts/generate_grad_aam_examples.py`; paper §§2.6, 3.5.

**Next:** Validate on paper-compatible compounds/tasks and assess chemical plausibility and attribution stability independently of the examples used to tune the implementation.

### 9. Multi-seed experiment settings and paper correspondence

**Paper:** Section 2.8 describes five-fold CV for Davis hyperparameter optimization; it does not prescribe five fixed seeds 42–46 as the principal final evaluation protocol. Paper results include study-specific evaluation splits, and section 3.3 includes additional split analyses. Repeating random initialization is useful variance analysis but is not interchangeable with five-fold CV.

**Code/artifacts:** `scripts/run_multiseed.ps1` launches seeds 42–46 sequentially into `results/davis/multiseed_retry_20261016/seed_<seed>/`, with 150 epochs × 50 steps, batch 32, LR 0.0005, patience 30, validation fraction 0.1, CUDA, and strict deterministic algorithms disabled. Python/NumPy/PyTorch/CUDA seeds and a seeded DataLoader generator are configured in `src/train.py`. The launcher writes a failure manifest; the aggregator excludes any run listed there.

**Status: DIFFERENT.** These are independent seed runs under a capped, non-paper configuration. They should be reported as exploratory multi-seed results, separately from the earlier baseline and from paper Table 3.

### 10. Tests, reproducibility, and missing components

**Paper:** The paper evaluates seven datasets, includes classification and regression tasks, cross-validation, model comparisons, ablations (dense connections, batch normalization, MCNN receptive field), and Grad-AAM analysis. It reports GPU hardware and tuning methodology in §2.8. These experiments establish scientific scope beyond a unit-tested implementation.

**Code/tests:** The repository has tests for preprocessing/model shapes, regression metrics, training/checkpoint flow, data isolation, Grad-AAM formula, and multi-seed aggregation. The multi-seed GPU runs use seeded RNGs but explicitly pass `--no-deterministic`, because a GPU backward operator lacks a deterministic implementation. This means runs are seeded but not guaranteed bitwise repeatable; GPU kernel order/hardware/software can cause small numerical differences. The core Davis pipeline inspected here does not implement all seven paper datasets, paper baselines, the paper’s full Optuna CV process, its reported ablation suite, or the ToxCast interpretability validation.

**Status: PARTIAL MATCH.** Tests provide implementation checks and regression protection; they do not prove equivalence to the paper. Reproducibility controls are present but strict deterministic execution is disabled in the saved GPU experiments. Core multi-benchmark, ablation, and scientific interpretation experiments are absent from the reviewed workflow.

**Evidence:** `tests/` (including `test_training.py`, `test_metrics.py`, `test_mgnn.py`, `test_mcnn.py`, `test_grad_aam.py`, `test_multiseed_aggregation.py`); `src/train.py:set_random_seed`, `configure_deterministic_execution`; `scripts/run_multiseed.ps1`; paper §§2.8, 3.4–3.5 and conclusion.

**Next:** Treat tests as software verification only; plan paper-matched CV and ablation/evaluation studies, and record hardware, software versions, split identifiers, configuration, and determinism limits for every run.

## Baseline and multi-seed results must remain distinct

The archived baseline in `results/davis/run_112_backup/evaluation_metrics_corrected.json` records test MSE 0.2570411, RMSE 0.5069922, CI 0.8790452, and `r_m²` 0.6817056, with best validation MSE 0.2323628 at epoch 91. That result is not pooled with seeds 44–46 here. The original paper Table 3 gives rounded Davis values MSE 0.217, CI 0.879, and `r_m²` 0.673. Similar CI alone does not establish reproduction.

## Hidden-channel meaning: equation-to-implementation review (2026-10-23; supersedes the mapping blocker above)

**Finding: the paper-level hidden width is supported as the output width \(h\) of each conceptual dense graph-convolution step.** The official RSC article's Eq. 1 describes a graph-convolution operation mapping input width \(d\) to output width \(h\). Eq. 3 defines each next multiscale feature as that operation applied to the concatenation of the original feature and all preceding dense outputs. Fig. 4 shows those concatenations. Table S3 calls its searched setting “The hidden channel number of each graph-convolutional layer” and selects 64 from [32,64,96,128,160]. Together, this is evidence for \(h\) as each conceptual dense step's appended feature width, rather than an inference from the matching value list. Sources: [official RSC article](https://pubs.rsc.org/en-us/content/articlehtml/2022/sc/d1sc05180f), §§2.2–2.3, Eqs. 1 and 3 and Fig. 4; [official RSC ESI PDF](https://www.rsc.org/suppdata/d1/sc/d1sc05180f/d1sc05180f1.pdf), Table S3. Online publisher-rendered text was inspected; the ESI was not downloaded or locally hashed.

| Architecture point | Paper / reference evidence | Local mapping and status |
|---|---|---|
| Conceptual graph-convolution output | Eq. 1 maps \(d\rightarrow h\); Eq. 3 concatenates each prior \(h\)-wide output before the next step | src/models/mgnn.py DenseLayer appends growth_rate; MGNN.hidden_channels is passed as that growth rate. **VERIFIED conceptual mapping:** S3 h → local growth_rate/appended feature width. |
| DenseLayer bottleneck | Paper Eqs. 1/3 do not specify a two-convolution bottleneck realization | Pinned references/mgraphdta_official/author_repo/regression/model.py DenseLayer performs input→growth_rate*bn_size→growth_rate; Davis regression uses bn_size=2. Local width 64 therefore gives physical outputs 128 then 64. **Reference-code behavior**, not the width assigned to every physical GraphConv by the paper. |
| Stem | Main-text equations identify input dimension \(d\) but do not give this implementation-specific stem number | Pinned release and local MGNN.conv0 use 32. **Verified reference/local value**, not Table S3 h. |
| Dense concatenation | Eq. 3 establishes initial feature plus per-step outputs | Local block width is input_width + layers_per_block*growth_rate. For S3 selected 3×8 and h=64: block outputs 544, 784, 904. **Verified local calculation.** |
| Transition | Article §2.3.2 / Eq. 4 says halve input channels; printed d+(N−1)h appears off by one relative to Eq. 3's initial feature plus N appended outputs | Local implementation and pinned code use input_width + N*h, then halve: transition outputs 272, 392, 452 for 3×8/h64. **Halving is supported; exact printed transition input dimension has an indexing inconsistency.** |
| MGNN output | Main-text readout Eq. 2 describes graph pooling but does not state numeric projection width | Pinned release uses filter_num*3 with filter_num=32 (96); local MGNN.fc outputs 96. **Reference/local implementation fact**, not a numeric value established by Eq. 2. |
| MGraphDTA fusion | Article architecture concatenates drug and protein representations | Local model concatenates 96+96 into width 192. Hidden channel changes do not change this projected fusion width. **Verified local implementation.** |

The resolved interpretation is specific: Table S3 h maps to the output width appended by each conceptual dense step, represented by local growth_rate; it does **not** mean every physical graph-convolution module, stem, or transition emits h. The author release's internal bottleneck explains the 2h intermediate while preserving h as the dense output. The code comment in src/models/mgnn.py and search parameter in src/paper_protocol.py match this mapping. Preserve default state-dict names/shapes at h=32; existing coverage is tests/test_mgnn.py::test_s3_hidden_channel_choices_preserve_depth_shapes_and_finite_readout, test_default_hidden_width_preserves_legacy_state_dict_shapes, and tests/test_mgraphdta.py::test_s3_hidden_channel_choices_produce_finite_scalar_affinity_predictions. These tests were inspected, not rerun; no architecture source/test changes were needed.

**Decision update:** the paper-level meaning of h is supported at the conceptual layer boundary by Eqs. 1 and 3, and local growth_rate is the structurally corresponding appended width. But the pinned released regression caller instantiates GraphDenseNet with its default growth_rate=32 and does not expose the authors' Table S3 tuning invocation showing that the selected 64 was bound to growth_rate.
